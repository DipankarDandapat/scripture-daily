Task 2: Implement WisdomOne OS Integration — Ambient Wisdom Layer

I want to introduce a premium Android experience called:

"WisdomOne — Ambient Wisdom Layer"

The objective is to make WisdomOne accessible throughout the user's daily phone experience, not just when they open the application.

A Bible verse should become part of the user's lock screen, always-on display experience, and home screen wallpaper.

1. Analyze Existing Functionality

Before implementation:

1. Inspect the existing Kotlin Android application.

2. Identify the current Daily Verse functionality.

3. Identify existing wallpaper and lock-screen verse implementations.

4. Understand how verses, images, user preferences, and backend APIs are stored.

5. Reuse existing components wherever possible.

Do not duplicate existing functionality.

2. Lock Screen Verse Integration

Implement an enhanced lock-screen verse experience.

Requirements:

  • Display a Bible verse on the Android lock screen.
  • Allow users to enable or disable this feature.
  • Allow users to configure verse refresh frequency:

o Every 1 hour

o Every 6 hours

o Every 12 hours

o Every 24 hours

  • Automatically change the verse based on the configured frequency.
  • Support different backgrounds and images.
  • Maintain readability and appropriate contrast.
  • Allow users to select their preferred visual style.

When a new verse appears, the background image should follow the user's image rotation preferences.

Avoid repeatedly displaying the same image until the available image collection has been exhausted, where practical.

3. Activity-Aware Wisdom

Introduce an optional activity-aware verse recommendation engine.

Suggested behaviour:

  • Walking: Energizing and motivational verses.
  • Running: Strength and perseverance verses.
  • Sitting or working: Focus and wisdom verses.
  • Night/resting: Peaceful and calming verses.

Use Android-supported activity recognition APIs where appropriate.

Requirements:

  • Request permissions only when necessary.
  • Make activity detection optional.
  • Provide a manual mode.
  • Do not continuously track users unnecessarily.
  • Minimize battery consumption.
  • Keep personal activity information private.

Activity detection should recommend a verse category rather than constantly changing the verse.

4. Always-On Display (AOD)

Explore support for displaying a single-line Bible verse on devices with Always-On Display functionality.

Requirements:

  • Display a short verse or selected verse excerpt.
  • Use minimal visual elements.
  • Minimize screen burn-in risks.
  • Avoid unnecessary background processing.
  • Respect Android and manufacturer restrictions.
IMPORTANT: Android does not provide a universal third-party API for controlling every manufacturer's Always-On Display. Implement only officially supported capabilities and provide a suitable alternative where direct AOD integration is unavailable.

Task 3: Replace Firebase Remote Config with Our Own Configuration API

Currently, the Android application uses Firebase Remote Config to control the application update screen.

I want to migrate this functionality to our own FastAPI backend configuration API because Firebase Remote Config may introduce additional costs.

The objective is to manage application configurations centrally through our backend.

1. Analyze Existing Implementation

Before making changes:

1. Inspect the existing Firebase Remote Config implementation.

2. Identify all configuration keys.

3. Identify where configuration values are fetched.

4. Identify how the app update screen is displayed.

5. Understand the existing minimum version and latest version validation.

6. Check whether any other features depend on Firebase Remote Config.

Do not remove Firebase Remote Config until all dependencies have been identified.

2. Create Configuration API

Implement a centralized configuration API in the existing FastAPI backend.

Suggested endpoint:

GET /api/v1/app/config

Adapt the response structure to the existing project conventions.

3. Application Update Logic

Implement the following scenarios:

Scenario 1: No Update Required

  • Current app version is supported.
  • Do not display the update screen.

Scenario 2: Optional Update

  • A newer version is available.
  • Display an optional update prompt.
  • Provide Update Now and Later buttons.

Scenario 3: Mandatory Update

  • Installed version is below minimum_supported_version.
  • Display a mandatory update screen.
  • Do not allow users to bypass the update.

Scenario 4: Latest Version

  • Application is already up to date.
  • Continue normally.

4. Configuration Management

The configuration should be managed from the backend.

Allow administrators to change:

  • Update enabled/disabled.
  • Minimum supported version.
  • Latest available version.
  • Force update status.
  • Update title.
  • Update message.
  • Play Store URL.

Do not require a new Android release when these values change.

5. Android Integration

Implement a centralized AppConfigManager.

Requirements:

  • Fetch configuration during application startup.
  • Avoid repeated API calls on every screen.
  • Cache the last successful configuration locally.
  • Handle API failures gracefully.
  • Use cached configuration when the backend is unavailable.
  • Define safe defaults for first-time offline launches.
  • Avoid blocking the main UI thread.

Consider the splash screen flow and ensure that users do not briefly enter the application before a mandatory update screen appears.

6. Remove Firebase Remote Config Dependency

After successful migration:

  • Remove Firebase Remote Config initialization.
  • Remove unused Firebase Remote Config dependencies.
  • Remove obsolete configuration fetching code.
  • Retain Firebase services that are still required, such as Analytics, Crashlytics, or Messaging.
  • Verify that no other feature depends on the removed functionality.

Task 4: Implement Full-Screen Maintenance Mode in WisdomOne:

I want to introduce a remote-controlled Maintenance Mode feature.

Sometimes we need to upgrade the backend, database, or application infrastructure.

During these periods, users should not be allowed to enter or use the application.

Instead, display a professional full-screen maintenance page controlled entirely by our backend configuration API.

1. Analyze Existing Architecture

Before implementation:

1. Inspect the existing Android application startup flow.

2. Inspect the AppConfigManager from the remote configuration implementation.

3. Identify the splash screen and navigation architecture.

4. Understand how application update screens are currently displayed.

5. Reuse the same configuration infrastructure.

Do not create a second independent configuration-fetching system.

2. Backend Configuration

Extend the existing endpoint:

GET /api/v1/app/config

The values must be controlled from the backend.

An administrator should be able to enable or disable maintenance mode without releasing a new Android application.

3. Full-Screen Maintenance UI

When maintenance_mode.enabled = true:

Display a dedicated full-screen page.

The user must not be able to access:

  • Home screen.
  • Daily Verse.
  • Journal.
  • Settings.
  • Profile.
  • Any other application functionality.

Design requirements:

  • Premium and minimal UI.
  • WisdomOne branding.
  • Attractive maintenance illustration.
  • Professional typography.
  • Clear title and description.
  • Optional estimated completion time.
  • Proper light/dark theme support.
  • Responsive layouts.

Suggested UI content:

Title:

We'll Be Back Soon!

Description:

We're currently upgrading WisdomOne to bring you a better experience.

Our team is working to restore the service as quickly as possible.

Estimated availability:

We'll be back around [configured time].

Primary action:

Close App

Optional secondary action:

Check Again

4. Application Behaviour

When maintenance mode is enabled:

1. Fetch the configuration before allowing access to the main application.

2. Navigate to the Maintenance Screen.

3. Clear or block access to the normal application navigation stack.

4. Disable back navigation to application screens.

5. Prevent deep links from bypassing maintenance mode.

6. Prevent notification clicks from opening normal application screens.

7. Do not allow users to enter the application until maintenance mode is disabled.

Close App:

  • Exit the application gracefully.
  • Use Android-supported activity finishing behaviour.
  • Do not force-stop or crash the application.

Check Again:

  • Fetch the latest backend configuration.
  • If maintenance is disabled, navigate to the normal application flow.
  • If maintenance is still enabled, remain on the maintenance screen.

5. Configuration Priority

Define a clear priority between application update and maintenance mode.

Recommended behaviour:

1. Fetch remote configuration.

2. Check mandatory application update.

3. If mandatory update is required, show the update screen.

4. Otherwise, check maintenance mode.

5. If maintenance is enabled, show the maintenance screen.

6. Otherwise, open the application normally.

Ensure the priority is implemented consistently.

6. Important Offline Behaviour

This is critical.

If the configuration API is unavailable:

  • Do not assume maintenance mode is enabled.
  • Use the last successful cached configuration where appropriate.
  • Define safe behaviour for first-time installation.
  • Display an appropriate connection error if the app cannot verify its operational status.
  • Provide retry functionality.
  • Avoid permanently locking users out because of a temporary network failure.

Document the trade-offs between cached configuration and maintenance enforcement.

7. Backend Administration

Provide an admin-controlled mechanism to:

  • Enable maintenance mode.
  • Disable maintenance mode.
  • Update maintenance title.
  • Update maintenance description.
  • Set estimated completion time.
  • Enable/disable retry.
  • Preview the maintenance configuration.
