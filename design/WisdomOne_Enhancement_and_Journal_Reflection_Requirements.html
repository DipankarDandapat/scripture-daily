Product & Engineering Specification

WisdomOne – App Enhancement & Journal Reflection

Consolidated UI/UX improvements, wallpaper and notification enhancements, Wisdom Tree, AdMob, centralized configuration, Journal Reflection, backend integration, and end-to-end testing requirements.

Project Objective

Implement the enhancements described in this document across the WisdomOne application. Use the design references in the project’s design folder, preserve existing functionality, and ensure that the frontend, backend APIs, database, and Android device integrations work together reliably.

Implementation approach: Review the existing project structure, database schema, APIs, and design assets before making changes. Reuse existing components and conventions where appropriate. Do not replace working functionality unnecessarily. Back up the project and database before making significant schema or data changes.

1. Homepage – Verse Sharing & Share Studio

  • Below the verse display box, the homepage currently displays Save, Share, and WhatsApp Status actions.
  • Keep the Save action, and remove the separate Share and WhatsApp Status buttons from the homepage.
  • Replace them with one primary button. Suggested labels are Spread the Light, Spread His Word, or Share with the World. Select the label that best fits the application’s tone and design.
  • When the user taps this button, open Share Studio.
  • Inside Share Studio, provide two actions: Share and WhatsApp Status.
  • When WhatsApp Status is selected, launch the WhatsApp Status sharing flow with the generated content so the user can review and publish it.
  • Remove or temporarily hide the Set as Wallpaper action from Share Studio.
  • Remove the separate Studio button from the homepage because Share Studio will be accessible through the new primary sharing button.

4. Lock Screen & Wallpaper – High Priority

The Lock Screen & Wallpaper feature is a core feature of the application and requires careful implementation and thorough device testing.

4.1 Existing behaviour and enhancement

Previously, users could enable Verse Wallpaper and Notifications from the homepage or Settings. The lock screen displayed the verse, and the background colour changed approximately every four to five hours. The enhanced experience should support tradition-based artwork as wallpaper backgrounds instead of relying only on changing background colours.

4.2 Tradition-based wallpaper gallery

  • Provide 20 popular, high-quality images for each supported tradition, such as Hinduism, Islam, Christianity, Buddhism, and other supported traditions.
  • Each tradition must have its own relevant image collection. Display images belonging to the user’s selected tradition.
  • Remove the separate Wallpaper Category section. The 20 images should be presented directly in the Gallery.
  • Allow horizontal scrolling through the gallery, displaying four images together in each visible group.
  • Ensure images are high quality, appropriately licensed, culturally relevant, and optimized for mobile performance.

4.3 Wallpaper behaviour options

Provide the following two mutually exclusive toggle options, using the specified labels and descriptions.

Option 1: Change Verse and Image Together
Default: ON
Description: “Automatically rotate through your selected artwork with every new verse.”
When enabled, update the verse and rotate the wallpaper image together whenever a new verse is displayed. Select images from the user’s chosen tradition.
Option 2: Keep Same Image
Default: OFF
Description: “Update the verse while keeping your current wallpaper.”
When enabled, allow the user to select an image from the 20 available images. When the verse changes, update only the verse text and keep the selected wallpaper image unchanged.
  • The two options must be mutually exclusive. Enabling one must automatically disable the other.
  • Both options may be OFF. In that case, display the verse using the existing multi-theme background colour functionality rather than an image.
  • Persist the selected mode and image so the behaviour remains consistent after the app is closed or restarted.

4.4 Lock screen preview

  • Improve the preview shown below the wallpaper behaviour toggles.
  • Show a realistic representation of how the verse and selected artwork will appear on the user’s device lock screen.
  • Include appropriate lock screen elements and ensure the verse remains readable against the selected image.
  • Update the preview immediately when the user changes the image, toggle selection, or wallpaper configuration.

4.5 Homepage integration

  • When the user enables the Verse Wallpaper & Notification toggle from the homepage, show the verse with artwork from the user’s selected tradition on the lock screen.
  • Initially use the first selected image from that tradition’s gallery.
  • Respect the wallpaper behaviour configured in Settings.
  • Keep wallpaper and notification permissions, platform restrictions, and actual device capabilities in mind. Do not indicate that a wallpaper has been applied unless the platform confirms the action.

4.6 Save & Apply Wallpaper

When the user taps Save & Apply Wallpaper, open a bottom sheet with these three choices:

  1. Set as Home Screen.
  2. Set as Lock Screen.
  3. Set as Home Screen & Lock Screen.

Apply the wallpaper according to the user’s selection and handle device-specific permissions or unsupported operations gracefully.

4.7 Wallpaper test scenarios

  • Enable and disable Verse Wallpaper.
  • Enable and disable Notifications.
  • Switch between Change Verse and Image Together and Keep Same Image.
  • Keep both wallpaper behaviour options OFF and verify multi-theme colour backgrounds.
  • Select different images from the gallery.
  • Change traditions and verify that only the relevant images are displayed.
  • Verify automatic verse and image rotation.
  • Verify that the same image is retained while verse text changes.
  • Apply wallpaper to the Home Screen, Lock Screen, and both screens.
  • Verify preview updates, permission handling, failure states, and compatibility across Android versions and device manufacturers.

Review the complete implementation specification before starting:

7.1 Centralized API-based configuration

Use a centralized backend API for advertisement configuration. The preferred approach is API-based configuration rather than Firebase Remote Config.

The API should provide the configuration required by the application, including:

  • AdMob App ID and Ad Unit IDs.
  • Advertisement format and placement identifiers.
  • Global and per-placement enable/disable status.
  • Banner size and layout configuration.
  • Advertisement frequency and display rules.
  • Any additional variables required to manage advertisements dynamically.

7.3 Advertisement placement strategy

  • Review the complete application and identify suitable advertisement placements.
  • Use formats appropriate to each screen and interaction.
  • Avoid intrusive placements that interrupt scripture reading, verse explanations, Journal Reflection, navigation, or critical user actions.
  • Avoid excessive advertisement frequency and accidental clicks.
  • Consider the needs of a global audience, different screen sizes, and varied device configurations.
  • Recommend additional placements where useful and exclude placements that could harm usability or trust.
  • Follow applicable AdMob policies, consent requirements, privacy requirements, and age-appropriate advertising rules.

7.4 Dynamic configuration and global switch

All advertisement settings should be manageable from the backend without requiring a new application release, wherever supported by the SDK and platform.

  • Enable or disable individual advertisement formats.
  • Enable or disable advertisements on specific screens.
  • Change supported banner sizes.
  • Adjust advertisement frequency and placement rules.
  • Update Ad Unit IDs.
  • Enable or disable individual placements.
Global switch: Implement ads_enabled = true/false. When set to false, no advertisements should be requested or displayed anywhere in the application, regardless of individual placement settings. When set to true, apply the individual configuration for each placement.

7.5 AdMob testing requirements

  • Use only official Google test Ad Unit IDs during development and testing.
  • Verify that all supported formats load and render correctly.
  • Test different screen sizes, network failures, loading errors, and empty ad responses.
  • Test the global enable/disable switch and individual placement settings.
  • Verify that backend configuration changes are applied without requiring an app update.
  • Keep test IDs separate from production IDs and prevent accidental use of live ads during development.
  • Provide a controlled process for replacing test IDs with production IDs before release.

8. Centralized Configuration API – Startup & Foreground Refresh

Some application configuration is currently retrieved through Firebase. Move the new configuration management requirements to the centralized API-based configuration system.

  • Implement a centralized key-value configuration API.
  • Retrieve required application configuration before navigating to the homepage on app launch.
  • Refresh the configuration whenever the app returns from the background to the foreground.
  • Apply updated configuration values dynamically, including advertisement settings.
  • Handle API failures, timeouts, and network connectivity issues gracefully.
  • Retain the last successfully fetched configuration as a fallback when the API is temporarily unavailable.
  • Use appropriate caching and refresh logic to avoid unnecessary API calls.
  • Design the API so additional application-level settings can be managed centrally in the future.
Startup behaviour: The app should not enter the homepage until the initial configuration request has completed or a defined fallback configuration has been applied. Avoid leaving users on an indefinite loading screen when the API is unavailable.

9. Journal Reflection – User Flow from Explain Verse

Refer to design/WisdomOne Reflection Flow.png for the intended UI/UX and user journey for creating a Journal Reflection.

  1. On the homepage, the user taps Explain this to me like I’m 5.
  2. The existing Explain Verse bottom sheet opens.
  3. Add a new button named Today’s Reflection at the bottom of the Explain Verse bottom sheet.
  4. When the user taps Today’s Reflection, open a new Reflection bottom sheet.
  5. Display a reflection question based on the meaning and message of that day’s verse.
  6. Allow the user to write their thoughts, feelings, or answer in a text area.
  7. Provide a Save Reflection button to save the response.
  • The question should encourage users to consider how the verse relates to their daily life, experiences, decisions, and personal growth.
  • Provide a clean, distraction-free writing experience.
  • Validate submissions appropriately and handle empty responses.
  • Provide clear feedback after a reflection has been saved successfully.
  • Avoid generic or unrelated questions when a verse-specific question is available.

10. Discovery – Journal Mode UI/UX Integration

Refer to design/Journal Reflection.png for the intended Journal Reflection design. Integrate this design into the existing Discovery → Journal section.

  • Display all previously saved reflections in the Journal section.
  • Organize entries chronologically by reflection date.
  • Each entry should display the reflection date, related verse or scripture reference, reflection question, and the user’s saved answer.
  • Allow users to open and view individual reflections.
  • Provide an Edit action so users can modify their saved answers.
  • Provide a Delete action so users can permanently delete a reflection.
  • Display a confirmation dialog before deleting a reflection.
  • Ensure edits and deletions are persisted to the backend and reflected in the UI.
  • When no reflections exist, show a meaningful empty state with an option or prompt to create the first reflection.

11. Reflection Question Management – Verse-based Questions

The proposed approach is to associate a reflection question with each verse.

  • Each verse should have a relevant reflection question.
  • When a verse is selected as the Verse of the Day, retrieve and display its associated reflection question.
  • Generate or curate questions based on the verse’s meaning, message, and practical teachings.
  • Questions should encourage personal reflection, self-improvement, gratitude, positive action, and real-life application.
  • Avoid repeating the same generic question across different verses.
  • Ensure the question matches the user’s selected tradition and language.
  • When the daily verse changes, display the question associated with the new verse.
  • If a verse does not have a question, provide a suitable fallback mechanism rather than showing a blank section.
  • Previously saved reflections must remain linked to their original verse and question even after the daily verse changes.

Example

Verse theme: A verse that teaches patience and controlling anger.

Reflection question: “Think about a recent situation where you felt angry. How could you have responded differently by practising patience?”

User response: The user writes their personal thoughts and saves them.
